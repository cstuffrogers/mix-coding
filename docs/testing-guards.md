# 守卫测试与探测器自检（怎么用）

> 这份文档只讲一件事：**怎么确认你脚下的绿色是真的**。
> 背景见 `DECISIONS.md` 的 ADR-012 ~ ADR-019。

## 1. 三层资产，三种跑法

| 层 | 命令 | 耗时 | 跑什么 | CI 是否跑 |
|---|---|---|---|---|
| 全量单测 | `npm test` | ~90s | 64 文件 / 725 例 | ✅ 是（根仓库 `npm test`） |
| 守卫测试 | `npm run test:guards` | ~3s | 5 文件 / 35 例 | ✅ 是（含在全量里） |
| 探测器自检 | `npm run detector:sweep` | ~2~3min | 12 个注入用例 × 2 次运行 | ❌ 否（手动，见第 5 节） |

工作目录都是 `claude-scene/`。

## 2. 守卫测试管什么

| 文件 | 守住的东西 | 红了说明 |
|---|---|---|
| `src/lib/scene-contract.test.js` | 场景里写的每个条件标识符、每个 action 名都有人实现；场景 `description` 完整；围栏/影响域步骤顺序 | 出现了悬空引用（恒假条件、未知动作）或半截描述 |
| `src/lib/not-run-status.test.js` | 处理器源码里禁止「裸字符串 return + 未执行/本轮未…」 | 某步没跑成却被记成 pass（第 9 种假绿） |
| `src/lib/docs-scene-alignment.test.js` | 文档承诺的命令、场景 JSON、命令入口三方一致 | 文档吹了不存在的命令，或新增场景没入口 |
| `src/commands/false-green-guard.test.js` | `skip` 不打绿 ✔、空结果不记 pass、五状态透传矩阵、产物顺序契约 | 输出层开始骗人 |
| `src/lib/sync-docs.test.js` | 文档同步：CRLF 不误报、写回保行尾、真缺标记要报、人工托管桶、僵尸目标、计数与锚点 | 文档同步又开始「报假警」或「改不动」 |

改场景 JSON、改输出层、改文档同步逻辑之后，先跑 `npm run test:guards`——3 秒内给你答案。

## 3. 探测器自检在验什么

守卫测试自己也可能空跑（断言写错、注入点过期、`expect(x).toBeTruthy()` 永远真）。
`scripts/detector-sweep.cjs` 的做法和变异测试（mutation testing）一样：

```
注入一条真实违规 → 跑该守卫测试 → 必须红
        ↓（内存备份复原）
      再跑一次 → 必须绿
```

输出读法：

| 输出 | 含义 | 怎么办 |
|---|---|---|
| `✅ 注入后红 / 复原后绿` | 这个守卫是真的会红 | 不用管 |
| `❌ 注入 exit=0 复原 exit=0` | **守卫是空的**：注入了违规它还是绿 | 去改那条断言 |
| `⚠ 注入点没匹配到（用例过期）` | 被测代码改过了，`from` 文本找不到 | 更新 `CASES` 里的 `from` |

最后一行汇总 `N/12 个探测器有效`，不满 12 时进程退出码为 1（可以接进脚本判断）。

## 4. 新增一条守卫测试：三步，缺一不可

1. **写断言**：放在对应领域文件里，断言要能点名（`expect(bad, 具体信息).toEqual([])`）。
2. **自证非空跑**：手工注入一次违规 → 必须红且点名 → 复原 → 必须绿。
3. **登记到探测器**：在 `claude-scene/scripts/detector-sweep.cjs` 的 `CASES` 里加一条，
   把第 2 步的注入动作固化下来：

```js
{
  name: '一句话说明这条守卫防什么',
  test: 'src/lib/你的测试.test.js',
  mutations: [{
    file: path.join(ENGINE, 'src/lib/xxx.js'),   // ENGINE = claude-scene，REPO = 仓库根
    from: '被改坏的原文（必须在文件里唯一且逐字一致）',
    to: '注入后的样子',
  }],
},
```

需要临时造文件（如「新增场景没入口」）用 `create: { file, text }`；
需要往文档追加一段冒充的承诺用 `append: { file, text }`。两种都会在复原时删掉/还原。

## 5. 什么时候跑探测器

| 场景 | 跑不跑 |
|---|---|
| 改了守卫测试或它的断言逻辑 | **必须跑** |
| 改了被守卫的源码（start.js / fence.js / sync-docs.js / 场景 JSON…） | 建议跑（会告诉你注入点是否过期） |
| 日常提交、CI | 不跑（太慢，且要改工作区） |
| 发版前 / 大重构后 | 建议跑一次留证据 |

## 5.5 接进 /review 的方式：只读产物，不跑变异测试

`/review` 场景里有一个步骤 **2.7 `detectorReport`**（条件 `code_review` / `full_audit`）。
它**不会**在审查过程中跑 detector-sweep —— 那东西会临时改写工作区，审查过程必须只读。
它只做一件事：读 `.claude/reports/detector-sweep-<stamp>.json` 并核对新鲜度。

| 现场 | 判定 | 含义 |
|---|---|---|
| 没有产物 / JSON 坏 / 缺字段 | `skip` | 「守卫是否真会红，本轮未验」——**不会**记成 pass |
| `failed` 非空 | `warn` | 某条守卫是空的（注入违规后仍绿），点名到用例 |
| `stale` 非空 | `warn` | 注入点过期，守卫可能和代码脱节 |
| 产物 HEAD ≠ 当前 HEAD | `warn` | 记录已过期，别拿旧结论充数 |
| 产物是在脏工作区跑的 | `warn` | 结论未必对应当前代码 |
| 以上都无 | `pass` | `12/12 有效（<sha>）` |

所以推荐流程：**工作区干净时**跑一次 `npm run detector:sweep` → 再跑 `/review`，
2.7 会给你一条 `pass`。如果改动后又没重跑，2.7 会把那条记录判成过期（`warn`），
这就是它存在的意义——把「没验」和「验过了」分清楚。

产物固定落在**仓库根**的 `.claude/reports/`；在 `claude-scene/` 子目录里被调起时，
2.7 会按 `git rev-parse --show-toplevel` 找到仓库根的那份，不会误报「没有记录」。

### 想一条命令搞定：`-S / --with-sweep`

```bash
node src/index.js start review --auto -S -p "审查当前代码"
```

带 `-S` 时，2.7 会在审查**开始前**现场跑一次 sweep（2~3 分钟），拿到新鲜产物再判。
审查本体依然只读 —— 注入式自检跑在它前面，不在它中间。
工作区脏时不跑，直接 `warn`「跳过现场自检」（脏着跑出来的记录一样不可信）。

不带 `-S` 时就是纯只读：有新鲜产物就 `pass`，没有就 `skip`，过期就 `warn`。

## 6. 三条坑

1. **别和其它会话并发跑**。它临时改写真实文件（跑完必复原，失败也在 `finally` 里复原），
   并发会让另一个会话读到注入态。
2. **跑完看一眼 `git status`**。正常应该是空的；不空说明某次复原失败（脚本会留下痕迹，别手忙脚乱 commit）。
3. **`from` 必须逐字一致且唯一**。含反斜杠/反引号时，用
   `['...', '...'].join(String.fromCodePoint(92))` 拼出反斜杠，别手写转义（手写十次错八次）。
