## 诚实评估：finding #1 是否达 Verified？

### v6 确实关闭了 v5 finding #1 的「19 处复杂度豁免」子缺口（成立）

v5 finding #1 Partial 的理由是「±50-line / 0-new-dep 仍靠人工 + 19 处 per-file 复杂度豁免」。这两道子缺口性质不同：

- **19 处复杂度豁免 = 机械可强制但被人为开口子**：`sonarjs/cognitive-complexity: ["error",15]` 规则本来能机械强制，但 19 处 `eslint-disable-next-line` 让规则在这些点上失效。v6 把这 19 处全部消除（grep 确认空），规则真正机械强制，**这道子缺口被实质关闭**。
- **±50-line / 0-new-dep = 本质非机械可强制**：行数增量和依赖增量是 git diff 维度，eslint（AST 级）无法在单文件 lint 阶段机械强制跨 commit 的增量边界。这需要 CI 侧 git diff 检查或 CodeGuardian MCP，eslint 规则层面不存在「机械强制」的可能。

### 但 v6 不等于 finding #1 跨过 Verified 门槛

finding #1 的全称是「declared change-safety 边界**部分**机械强制」。Verified 要求「declared 边界**机械强制**」——即所有声明的边界（≤±50 行 / 0 新依赖 / 复杂度 ≤130%）都被机械强制。v6 关闭了复杂度豁免，但：

- **±50-line / 0-new-dep 仍靠 git diff 人工**：这两道边界至今没有机械强制机制（无 CI git diff 门禁证据、无 CodeGuardian 强制证据）。证据包未观察到行数/依赖增量的机械拦截。
- **finding #1 的「部分机械强制」定性未变**：从「复杂度有豁免 + 行数/依赖靠人工」收敛为「复杂度真机械强制 + 行数/依赖仍靠人工」。机械强化的范围扩大了（复杂度从假强制变真强制），但「部分」二字仍成立——仍有两道声明边界靠人工。

### finding #1 状态判定

- **不达 Verified**：Verified 要求所有声明边界机械强制。±50-line / 0-new-dep 仍靠人工。
- **从 Partial 强化为「Partial（接近 Verified）」**：v5 是「两道子缺口」（豁免 + 人工边界）；v6 是「一道子缺口」（仅人工边界）。复杂度这道从「假机械强制（有豁免）」升级为「真机械强制（0 豁免）」。**这是实质进步，更接近 Verified，但未跨档**——因为 finding #1 的「部分」定性靠的是「还有边界靠人工」，而人工边界这道缺口 v6 未动。
